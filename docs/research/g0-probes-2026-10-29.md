# G0 probes: time control, saves and action retries (2026-10-29)

- **Performed by:** AI Collaborator Claude, with the maintainer's permission to use the current fort as a disposable fixture.
- **Environment:** the pinned pair from the [reuse audit](reuse-audit-2026-10-29.md), plus dfhack-mcp 1.4.1.
- **Scripts:** [`experiments/g0/`](../../experiments/g0/). Run logs are kept locally and are not committed.
- **Evidence label:** everything below is **Verified** on this fixture unless marked otherwise. One fixture is not proof of general reliability.

## Fixture

The fort is "Foughtmines", the **new-player tutorial** embark: year 100, spring, 7 citizens, in the save folder `region1`. A tutorial fort skips world generation, so it is **not** a lifecycle fixture. Tutorial state is readable through `world.active_tutorial`, `plotinfo.tutorial_seen` and `main_interface.help.open`. DFHack ships a `hide-tutorials` tool. The baseline save was backed up before any write.

## Time control (Q-02)

| Test | Result |
|---|---|
| A one-day step: 1,200 ticks requested | 1,200 elapsed, overshoot 0, cause `controller_timer`, 12.1 s wall time |
| Ten consecutive 600-tick steps | **10 out of 10** were exact, with overshoot 0. Each took about 6.2 s, roughly 99 ticks per second at the 100 FPS cap. |
| An external pause injected 5 s into a 3,000-tick step, as if a human pressed pause | The step stopped at 506 ticks. The cause was reported as `unknown`, correctly, since nothing attributable happened. The pending timer was **cancelled**, and that was confirmed afterwards. |
| DF pausing itself: a caravan forced with `force Caravan` during a 12,000-tick step | The step stopped after 3 ticks. Causes were `popup_opened` and `pausing_announcement` (`FIRST_CARAVAN_ARRIVAL`), and the timer was cancelled. |
| Stepping while a popup is open | **Blocked.** 0 ticks elapsed. The game re-pauses immediately. `step.lua` now refuses to start and returns the popup's text. |
| Dismissing the popup | Simulated `LEAVESCREEN` and `SELECT` keys did **not** dismiss it. Removing it from `world.status.popups` did, and the next step ran a clean 600 ticks. |
| Controller death mid-step: begin a 1,200-tick step, stop polling, reconnect 16 s later | The step ended at exactly 1,200 ticks, and the full status could be recovered from in-game state. |
| A one-off anomaly | The very first step stopped after 1 tick, with no popup, help window or report. It was reported as `unknown`. It did not recur in 15 later steps, including steps right after a save. **Unexplained.** |

**What this means for the design:**
- **Pause causes come from box popups.** In v0.53.16, game-pausing announcements use `BOX` / `DO_MEGA`, which 35 types set. The `PAUSE` flag is set on none. Pause attribution should watch the popup list and the `DO_MEGA` flags.
- **A popup open at step start must be reported as blocked,** not as a new cause.
- **Popup dismissal is a controller responsibility,** and the dismissed text should be logged as an event.
- **The in-game timer makes steps survive a controller crash,** but not a game crash. The ledger still needs storage outside the game.

## Durable saves (Q-03, Q-10)

| Observation | Value |
|---|---|
| `quicksave` command return | Immediate, about 0.02 s, and asynchronous |
| Files written | About 700 files, from about 0.3 s to about 10 s after the call. Consistent across 4 saves. |
| **Completion signal** | DFHack RPC **blocks for about 8 s while saving**. The first response afterwards coincides with the files settling, so "RPC responsive again plus files stable" is a usable completion check. |
| Slot rotation | `autosave 1`, then 2, then 3, then **back to 1**, so slots are overwritten. `region1` is never written by quicksave. |
| Loaded-save identity | After a quicksave, `world.loaded_save_path` points to the autosave slot just written. |

**What this means for the design:**
- **Copy checkpoints out.** `checkpoint` must copy the finished slot into the controller's own checkpoint store, and record which slot it was.
- **The save path can't identify a session alone.** Reload and verify-loaded-session must not rely only on `loaded_save_path`.
- **Loading is untested.** A save hasn't been loaded without the UI, and there is no `load-save` command.

## Action retries through dfhack-mcp (Q-04)

| Test | Result |
|---|---|
| Preview, then apply, a `ConstructBed` order | Applied with a readback and an undo handle. The order is `validated: false` and `active: false`, because the fort has no manager. **Applied is not actionable**, as DEC-004 anticipates. |
| Reusing a confirm token | Refused: "invalid or expired confirm_token; tokens are single-use". |
| Previewing an identical order | `would_duplicate: true` with `duplicate_of: 0`, **but a new token is still issued**. Duplicate detection is advisory. |
| Killing the server during apply | At delays of 0 and 0.01 s the order did not land. **From 0.02 s onward it landed, but the client never received the receipt.** Five naive retries created five identical orders. |
| Cancelling them with `work_order_cancel` | Preview then apply, 5 out of 5 succeeded, each with a `faithful: true` recreate spec. |
| Invalid job types (`BrewDrink`, `MakeTable`) | Preview blocked, and no token was issued. That behavior is correct. The tool's own schema uses `MakeTable` as an example, but it isn't a job type in this version; it's an upstream doc bug. |

**What this means for the design:**
- **Retries must reconcile first.** Before any retry, read `work_order_list` and match the intended order. This is DEC-004's `unknown`, followed by reconciliation, now shown to be necessary.
- **Idempotency is the controller's job.** The controller must enforce its own idempotency keys, because the upstream duplicate check doesn't block.
- **New gap: there are no reaction orders.** In this version brewing is a custom reaction, not a job type, and `work_order_create` takes no reaction argument. DFHack's own `workorder` command accepts reaction orders. This is documented, not tested. R2's prepared-save brewing experiment therefore needs a controller-side order path, or an upstream change.
