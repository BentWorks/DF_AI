## Review by AI Collaborator Claude

**Accepted as written:** wrapper ownership (DEC-003), separate execution and goal evidence (DEC-004), time and recovery (DEC-005), spatial planning, endings, evaluation and validation order.

**Accepted with amendments:** the v1 boundary and the tool catalogue, as below.

### A1. Goal/loss precedence

A goal is achieved only when its full sustained interval completes with the
fortress alive. If loss evidence appears at or before the tick where that
interval would complete, the outcome is `fortress_lost`. When the evidence is
ambiguous, for example the bridge drops at that moment, the outcome is
`infrastructure_failure` until reconciled. This rule is conservative and needs
no tie-breaking clock.

### A2. A lifecycle feasibility gate for the v1 boundary

The v1 target remains fixed-profile startup through G1, and it should not be shrunk. The evidence so far is uneven:

| Lifecycle step | Evidence | Label |
|---|---|---|
| World generation | DF has a command-line generator, `-gen <id> <seed> <param set>`. It creates a world silently and exits. | Documented ([wiki](https://dwarffortresswiki.org/index.php/Command_line)). The syntax on the pinned version must be checked against its bundled `command_line.txt`. |
| Embark site and setup | No DFHack tool automates the embark screens. Helpers exist, including `gui/embark-anywhere`, `embark-skills` and `deep-embark`. The `on-new-fortress` hook runs commands on the first tick after embark. Driving the screens would need simulated input. | Documented helpers. Automation itself is assumed. |
| Load save | Codex reports that `load-save` is marked unavailable in current docs. | Documented ([load-save](https://docs.dfhack.org/en/stable/docs/tools/load-save.html)) |

**Amendment:** Add a lifecycle spike before the full-startup milestone.
- **Pass:** Ten consecutive unattended runs create a world, embark with the fixed profile, and reach fortress tick 1. Each run is verified by sensors.
- **Fail:** The maintainer decides between investing in input automation and allowing a clearly labeled, human-assisted embark step in v1. The v1 goal is not silently redefined.

### A3. Minimum G1 tool catalogue

R1 lists tool categories. For G1 to be measurable, I propose this concrete
minimum. Where dfhack-mcp is believed to cover a tool, it is noted; all of
these coverage claims are Documented, not Verified.

| Tool | Purpose | Coverage |
|---|---|---|
| `observe` | Compact fort status, stocks and trends, needs, health, jobs, threats | dfhack-mcp sensors |
| `events_since(cursor)` | Announcements and reports after a cursor | **Gap.** `chronicle()` is a feed with no cursor. |
| `inspect_region` | A bounded ASCII window of a z-level | dfhack-mcp `tile_region` |
| `find_sites(spec)` | Candidate areas meeting size, material and reachability needs | **Gap** |
| `designate(blueprint, anchor, mode)` | Dig and zone | dfhack-mcp `blueprint_apply` |
| `construct(blueprint, anchor)` | Build and place: workshops, furniture, stockpiles | **Gap.** Build and place modes are rejected in dfhack-mcp v1. |
| `configure_stockpile` | Stockpile settings | **Gap** |
| `set_farm_crops` | Choose crops per plot and season | **Gap** |
| `work_order_create` / `work_order_cancel` | Production | dfhack-mcp |
| `assign_work_detail` | Labor | dfhack-mcp |
| `checkpoint` / `verify_checkpoint` | A durable save, confirmed to have landed | **Partial.** `game_save` only confirms dispatch. |
| `pause` / `advance_until` | Bounded time with stop evidence | **Gap** |
| `action_status(id)` / `goal_status(id)` | Reading back the ledger | **Gap.** This belongs to the controller. |
| `lifecycle_*` | World, embark and loss detection | **Gap.** See A2. |

Military, trade, healthcare and justice tools are deferred to G2 and G3.

### A4. Benchmark budgets

Each scenario should declare `max_model_calls`, `max_input_tokens`,
`max_wall_time` and `max_game_ticks`. G1 defaults should be set after G0
measures real step latency, not guessed now.
